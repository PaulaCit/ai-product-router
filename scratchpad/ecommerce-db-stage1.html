Árvore do Repositório

Artefato 3a — Migration V001

DDL — Tabela categories

Implementa o padrão Adjacency List: cada linha conhece seu pai via parent_id. Simples de escrever e manter; navegação de árvore completa é feita com WITH RECURSIVE. A flag is_leaf evita a recursão para nós-folha na maioria das queries de leitura.

Por que Adjacency List e não Nested Sets ou Closure Table? Com Jitterbit fazendo inserções em batch, a simplicidade de DML do Adjacency List supera os benefícios de leitura das outras abordagens. A WITH RECURSIVE performa bem até ~10.000 categorias no PostgreSQL — escala suficiente para a maioria dos marketplaces verticais.
db/migrations/V001__create_categories.sql SQL 
-- ============================================================
-- V001: Tabela de categorias (Adjacency List)
-- Suporta árvore de profundidade arbitrária.
-- ============================================================

CREATE TABLE IF NOT EXISTS categories (
    -- PK auto-incremental (UUID seria alternativa para UUIDs externos do Jitterbit)
    id              BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,

    -- Nome da categoria, único dentro do mesmo nível pai
    name            VARCHAR(120) NOT NULL,

    -- NULL indica nó raiz (Departamento de 1º nível)
    parent_id       BIGINT REFERENCES categories(id) ON DELETE RESTRICT,

    -- TRUE quando não possui filhos; atualizado via trigger ou app
    is_leaf         BOOLEAN NOT NULL DEFAULT FALSE,

    -- Slug para URL/SEO: "lavadoras-de-alta-pressao"
    slug            VARCHAR(150) NOT NULL,

    -- Metadados de auditoria
    created_at      TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at      TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

-- Unicidade: mesmo nome não pode aparecer duas vezes no mesmo nível
CREATE UNIQUE INDEX uq_categories_parent_name
    ON categories (
        COALESCE(parent_id, -1),  -- -1 representa "sem pai" (raiz)
        name
    );

-- Índice de navegação: busca filhos de um nó (usado em browse)
CREATE INDEX idx_categories_parent_id ON categories (parent_id);

-- Índice para lookup por slug (rota /categoria/automotivo/acessorios)
CREATE UNIQUE INDEX uq_categories_slug ON categories (slug);

-- Trigger: atualiza updated_at automaticamente
CREATE OR REPLACE FUNCTION fn_set_updated_at()
RETURNS TRIGGER LANGUAGE plpgsql AS $$
BEGIN
    NEW.updated_at = NOW();
    RETURN NEW;
END; $$;

CREATE TRIGGER trg_categories_updated_at
BEFORE UPDATE ON categories
FOR EACH ROW EXECUTE FUNCTION fn_set_updated_at();
Artefato 3b — Migrations V002 e V003

DDL — Produtos e Tabela Pivot

O campo primary_category_id em products define o nó principal — aquele que determina regras fiscais e comissão. A tabela pivot product_secondary_categories mapeia os nós de descoberta (N:N).

db/migrations/V002__create_products.sql SQL 
-- ============================================================
-- V002: Tabela de produtos
-- primary_category_id: nó principal (regras, comissão, fiscal)
-- ============================================================

CREATE TABLE IF NOT EXISTS products (
    id                   BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,

    -- Identificador externo do ERP/Jitterbit (para upsert idempotente)
    external_sku         VARCHAR(80) UNIQUE,

    title                VARCHAR(255) NOT NULL,
    description          TEXT,

    -- Nó principal: define regras fiscais, comissão e reporting
    primary_category_id  BIGINT NOT NULL REFERENCES categories(id)
                         ON DELETE RESTRICT,

    -- Preço base em centavos (evita float arithmetic)
    price_cents          INTEGER NOT NULL CHECK (price_cents >= 0),
    currency             CHAR(3) NOT NULL DEFAULT 'BRL',

    status               VARCHAR(20) NOT NULL DEFAULT 'draft'
                         CHECK (status IN ('draft', 'active', 'paused', 'deleted')),

    created_at           TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at           TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

CREATE INDEX idx_products_primary_category
    ON products (primary_category_id);

CREATE INDEX idx_products_status
    ON products (status)
    WHERE status = 'active';  -- índice parcial: só produtos ativos

CREATE TRIGGER trg_products_updated_at
BEFORE UPDATE ON products
FOR EACH ROW EXECUTE FUNCTION fn_set_updated_at();
db/migrations/V003__create_pivot_table.sql SQL 
-- ============================================================
-- V003: Pivot N:N — categorias secundárias (descoberta/SEO)
-- Um produto pode aparecer em múltiplos nós de navegação.
-- ============================================================

CREATE TABLE IF NOT EXISTS product_secondary_categories (
    product_id   BIGINT NOT NULL REFERENCES products(id)    ON DELETE CASCADE,
    category_id  BIGINT NOT NULL REFERENCES categories(id) ON DELETE RESTRICT,

    -- Quando esta associação foi criada (rastreabilidade Jitterbit vs Dashboard)
    created_at   TIMESTAMPTZ NOT NULL DEFAULT NOW(),

    PRIMARY KEY (product_id, category_id)
);

-- Índice reverso: dado uma categoria, quais produtos ela contém
CREATE INDEX idx_psc_category_id
    ON product_secondary_categories (category_id);

-- Regra: nó secundário não pode ser o mesmo que o nó principal
ALTER TABLE product_secondary_categories
ADD CONSTRAINT chk_no_duplicate_primary
CHECK (
    category_id NOT IN (
        SELECT primary_category_id FROM products
        WHERE id = product_id
    )
);
Atenção — constraint de performance: A CHECK com subquery em V003 é avaliada a cada INSERT. Em volumes acima de 10k inserções/batch via Jitterbit, considere substituí-la por uma trigger BEFORE INSERT ou mover a validação para a camada de serviço.

Artefato 4

Query Recursiva — Breadcrumbs Completos

A WITH RECURSIVE percorre o Adjacency List de filho para raiz, acumulando os nomes. O resultado final inclui o caminho da categoria principal e todos os caminhos secundários do produto.

breadcrumbs_by_product.sql SQL 
-- ============================================================
-- Retorna todos os breadcrumbs de um produto (principal + secundários)
-- Parâmetro: :product_id = 1 (Lavadora de Alta Pressão)
-- ============================================================

WITH RECURSIVE

-- CTE 1: sobe a árvore para qualquer categoria inicial
category_path (
    start_category_id,  -- mantém o ponto de entrada da recursão
    id,
    name,
    parent_id,
    depth,
    path_text           -- breadcrumb acumulado (raiz > ... > folha)
) AS (
    -- Caso base: começa no nó-folha
    SELECT
        c.id                AS start_category_id,
        c.id,
        c.name,
        c.parent_id,
        0                   AS depth,
        c.name::TEXT        AS path_text
    FROM categories c
    WHERE c.id IN (
        -- Nó principal do produto
        SELECT primary_category_id FROM products WHERE id = :product_id
        UNION ALL
        -- Nós secundários
        SELECT category_id FROM product_secondary_categories
        WHERE product_id = :product_id
    )

    UNION ALL

    -- Caso recursivo: sobe para o nó pai
    SELECT
        cp.start_category_id,
        parent.id,
        parent.name,
        parent.parent_id,
        cp.depth + 1,
        parent.name || ' > ' || cp.path_text  -- constrói "Raiz > ... > Folha"
    FROM categories parent
    JOIN category_path cp ON cp.parent_id = parent.id
),

-- CTE 2: pega apenas a linha mais alta (raiz) de cada caminho
final_paths AS (
    SELECT DISTINCT ON (start_category_id)
        start_category_id,
        path_text,
        depth AS total_levels
    FROM category_path
    ORDER BY start_category_id, depth DESC  -- profundidade máxima = caminho completo
)

-- Resultado final: junta com informação de tipo do nó
SELECT
    p.id                                        AS product_id,
    p.title                                     AS product_title,
    CASE WHEN fp.start_category_id = p.primary_category_id
         THEN 'principal'
         ELSE 'secundario'
    END                                         AS category_type,
    fp.start_category_id                        AS leaf_category_id,
    fp.path_text                                AS breadcrumb,
    fp.total_levels
FROM products p
CROSS JOIN final_paths fp
WHERE p.id = :product_id
ORDER BY category_type DESC, fp.start_category_id;

Artefato 5a

Lógica de Negócio — Nó Principal vs. Nós Secundários

A separação entre nó principal e nós de descoberta não é apenas técnica — ela reflete responsabilidades de negócio distintas que precisam ser preservadas independentemente de como o produto chega ao sistema.

Dimensão Nó Principal (primary_category_id) Nós Secundários (product_secondary_categories)
Cardinalidade Exatamente 1 por produto 0 a N por produto
Comissão Define a taxa de comissão do marketplace (ex: Limpeza = 12%) Não afeta comissão
Fiscal / NCM Mapeado para código NCM na NF-e do seller Ignorado no fiscal
Regras de conteúdo Determina campos obrigatórios (ex: tensão em Eletro) Não impõe validações
SEO / Browse URL canônica: /lavadoras-de-alta-pressao/produto-x URLs alternativas e listagens cruzadas
Relatórios de GMV Atribuição de receita ao departamento principal Não aparece em relatórios de GMV
Regra de negócio crítica: um produto jamais pode ter o mesmo nó como principal e secundário simultaneamente. A constraint chk_no_duplicate_primary em V003 e a validação na camada de serviço garantem essa integridade em dois níveis independentes.
Artefato 5b

Fluxos de Integração

Fluxo Jitterbit (Batch): o adaptador recebe um payload JSON do ERP, normaliza o campo de categoria e executa um INSERT … ON CONFLICT (external_sku) DO UPDATE — garantindo idempotência. O nó principal vem mapeado do campo category_code do ERP; os nós secundários chegam como array discovery_categories[] e são inseridos em batch na pivot.

api/integrations/jitterbitAdapter.js — lógica de upsert JavaScript 
// Recebe payload do Jitterbit e faz upsert idempotente
async function upsertProductFromBatch(payload, db) {
  const { external_sku, category_code, discovery_categories, ...fields } = payload;

  // Resolve category_code do ERP → id interno
  const primaryId = await db.one(
    'SELECT id FROM categories WHERE slug = $1 AND is_leaf = TRUE',
    [category_code]
  );

  // Upsert principal — ON CONFLICT garante idempotência
  const product = await db.one(
    `INSERT INTO products (external_sku, primary_category_id, ...)
     VALUES ($1, $2, ...)
     ON CONFLICT (external_sku) DO UPDATE
       SET primary_category_id = EXCLUDED.primary_category_id,
           updated_at = NOW()
     RETURNING id`,
    [external_sku, primaryId.id, /*...*/]
  );

  // Substitui nós secundários em bloco (delete + insert)
  await db.tx(async t => {
    await t.none(
      'DELETE FROM product_secondary_categories WHERE product_id = $1',
      [product.id]
    );
    if (discovery_categories?.length) {
      const rows = discovery_categories.map(slug => ({ product_id: product.id, slug }));
      // pg-promise helpers para INSERT em batch
      await t.none(db.$helpers.insert(rows, ['product_id', 'category_id'],
        'product_secondary_categories'));
    }
  });
}

Fluxo Dashboard do Vendedor: a API expõe um endpoint PATCH /products/:id/categories que aceita primary_category_id e secondary_category_ids[]. A validação de negócio (nó não pode ser principal e secundário ao mesmo tempo; nó principal deve ser is_leaf = TRUE) é feita na camada de serviço antes do SQL, devolvendo erros 422 com descrição legível para o frontend do Dashboard.

Regra de acesso por fluxo: o Jitterbit usa uma role PostgreSQL role_jitterbit com permissão INSERT, UPDATE apenas em products e product_secondary_categories. O Dashboard usa role_api com as mesmas permissões mais SELECT em categories. Nunca ambos usam o superusuário.
Artefato 5c

Como Rodar

Terminal — setup completo BASH 
# 1. Clone e configure variáveis de ambiente
cp .env.example .env
# Edite .env com suas credenciais desejadas

# 2. Suba o PostgreSQL
docker compose -f infra/docker-compose.yml up -d postgres

# 3. Aguarde o healthcheck ficar healthy (~10s)
docker compose -f infra/docker-compose.yml ps

# 4. Aplique as migrations em ordem
psql $DATABASE_URL -f db/migrations/V001__create_categories.sql
psql $DATABASE_URL -f db/migrations/V002__create_products.sql
psql $DATABASE_URL -f db/migrations/V003__create_pivot_table.sql

# 5. Popule com dados de exemplo
psql $DATABASE_URL -f db/seeds/S001__categories_tree.sql
psql $DATABASE_URL -f db/seeds/S002__sample_products.sql

# 6. (Opcional) Abra o pgAdmin em http://localhost:5050
docker compose -f infra/docker-compose.yml --profile tools up -d pgadmin

# 7. Teste a query de breadcrumbs
psql $DATABASE_URL -v product_id=1 -f breadcrumbs_by_product.sql
Com Flyway (recomendado para CI/CD): renomeie os arquivos de migration para o padrão V1__desc.sql, V2__desc.sql e execute flyway -url=jdbc:postgresql://... migrate. O Flyway registra cada migration aplicada na tabela flyway_schema_history e impede re-execução.
Nunca execute os seeds em produção. Os arquivos S0xx__*.sql são exclusivos para ambientes de desenvolvimento e staging. Em produção, os dados vêm via Jitterbit ou do Dashboard do Vendedor.
